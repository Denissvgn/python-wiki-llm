### FINDING-01: the uncertainty is valid; its route projection is not

The reported `observability_alerts` source still emits a `GET` operation with
`path=None` and `unknowns=[{field: path, reason: not_statically_resolvable}]`.
The [static contract builder](../../src/llm_wiki_cli/services/api_contracts.py#L960)
is explicit about that uncertainty. The
[attachment adapter](../../src/llm_wiki_cli/services/api_contracts.py#L1860) copies
the null into a field documented as resolved routes, and
[artifact validation](../../src/llm_wiki_cli/services/knowledge_artifacts.py#L1392)
correctly rejects it.

| Fixture command | Result |
|---|---|
| Literal-path bootstrap | Exit 0; all three native metadata files committed |
| Dynamic-path bootstrap with `--api-contracts` | Exit 1; five Markdown files remain, no committed native trio |
| Dynamic-path bootstrap without `--api-contracts` | Exit 1; four Markdown files remain, no committed native trio |
| Sync after changing the valid fixture to a dynamic path | Exit 1; prior metadata bytes preserved, wiki content changed |

The exact error is
`surface_index.flows[0].routes[0].path: must be a non-empty string`.
The CLI reports this error normally; the reproduction does not show an uncaught
Python traceback. Its scope is broader than an opt-in API-contract page: the
shared route metadata also affects the default full bootstrap.

Do not substitute a fake endpoint or make the stored-route validator accept
null. Preserve unresolved operation evidence outside the concrete route list.
The changed wiki paths in the observation record also show why preserving
metadata files alone cannot be described as whole-wiki rollback.

### FINDING-02: the same false binding exists in two resolvers

Both [_resolve_call](../../src/llm_wiki_cli/services/extraction_service.py#L2622)
and [_resolve_call_observation](../../src/llm_wiki_cli/services/extraction_service.py#L2733)
search the repository-wide symbol index when a bare name has no earlier match.
In the fixture, introducing an unrelated `def set(key, value)` changes a
file-less `set()` leaf into an internal edge and adds the other service to
`modules_touched`.

The actual reported edge also reproduces from the selected source files:
`services/autotrade-service/src/core/permissions.py:get_user_permissions_set`
calls `services/order-router/src/core/balance_cache.py:set` in both analyzer
representations, at the source `set()` call on line 326. The generated report
artifacts for both `http-get_dashboard` and `http-get_leverage_options` contain
the corresponding balance-cache hop.

Additional controlled cases confirm the broader binding defect: an unimported
`helper()` binds to an unrelated `helper`, and importing `Client` from an
unresolved external SDK binds to an unrelated internal `Client` through
[_resolve_import_candidates](../../src/llm_wiki_cli/services/extraction_service.py#L2384).
Local and explicitly imported `set` shadows are valid controls and must remain
internal when justified. Therefore a blanket builtin blacklist or a change to
only one resolver is insufficient. Merely restricting a fallback to a service
directory still does not establish a Python binding.

These are fabricated analyzer edges, not actual network/process calls made by
the target application. VB-03 corrected display identity; it did not remove
this separate repository-wide binding fallback.

### FINDING-03: global aliases become asserted import-time edges

[ModulePathResolver.build](../../src/llm_wiki_cli/services/imports.py#L53)
indexes bare stems and path suffixes. For `service_b/utils/logging.py`,
[_suffix_candidates](../../src/llm_wiki_cli/services/imports.py#L287) still adds
both `utils/logging` and `logging`, even if the explicit `path.stem` element
were removed.

The fixture's API import of stdlib `logging` resolves to both nested utilities.
Those utilities each import `logging`, so the
[dependency graph](../../src/llm_wiki_cli/services/dependencies.py#L126) creates
mutual import-time edges and the load-order renderer emits an indeterminate
cycle group. Detailed dependency observations label the same candidates
`ambiguous`, exposing an additional distinction the legacy graph does not
preserve. In the reported-source subset, the exact four logging utilities form
the same false cycle.

This differs from the previously excluded TYPE_CHECKING finding: an actual
runtime-cycle warning is produced here from incorrect target resolution.
Controls verify that explicit relative imports resolve correctly and that a
top-level local `logging.py` can legitimately shadow stdlib logging. A blanket
stdlib exclusion would therefore be wrong. Removing one stem insertion also
leaves the suffix backdoor and the ambiguity-to-edge promotion untouched.
