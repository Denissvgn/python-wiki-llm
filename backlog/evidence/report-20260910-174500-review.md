### FINDING-01: intact evidence becomes an unhelpful diagram label

The current source replay reproduces the reported sequence diagram exactly.
The data-flow diagram also reproduces its labels and edges; its two module
click links are absent because the bounded renderer probe does not supply a
module-page map. Both diagrams omit `.build` from the long target label.

The actual path is:

1. [_call_record](../../src/llm_wiki_cli/extractors/python_extractor.py#L170)
   captures `name="build"` and the full `attr="_ReportBuilder(...).build"`.
   The extractor does **not** truncate that expression.
2. [resolve_python_call](../../src/llm_wiki_cli/services/python_calls.py#L151)
   leaves the returned-object method unresolved. The separate constructor
   call has a justified internal class target. Both the legacy edge and
   detailed observation preserve the full expression and method name.
3. [_flow_actors](../../src/llm_wiki_cli/services/bootstrap_runtime.py#L2497)
   selects the full unresolved expression as the display label as well as
   retaining it in the scoped participant identity. The shared sequence and
   data-flow presentation consume that long label.
4. [_normalize_display_text](../../src/llm_wiki_cli/services/diagrams.py#L68)
   keeps only the first 159 characters plus an ellipsis. Long arguments push
   the actual method beyond this intentional 160-character limit.

| Controlled case | Method visible in diagrams | Full method retained in evidence | Resolution |
|---|---|---|---|
| `Builder(long_arguments...).build()` | No | Yes | Method unresolved; constructor internal |
| `Builder().build()` | Yes | Yes | Same resolution as the long form |
| `factory(long_arguments...).build()` with a parameter factory | No | Yes | Both calls unresolved |
| Long receiver followed separately by `.build()` and `.finish()` | Neither method visible; displayed target labels match | Yes; distinct raw targets and participant IDs | Methods unresolved; constructor internal |

This is a presentation bug, not evidence of a dropped method observation or
an incorrect internal call edge. Two participant identities are appropriate
for the constructor and the unresolved returned-object method; merging them
would conceal uncertainty. The 160-character cap is intentional, but feeding
it an argument-heavy expression hides the most useful target information.
The separate 30-interaction budget is unrelated to this small reproduction.

The report's suggested `ast.Name` constructor shortcut is insufficient:
that name can be a function, a parameter factory, an alias, or a shadowed
binding. Even a known class call does not by syntax alone prove the runtime
type of the returned object. The planned fix compacts display text while
preserving VB-06's binding decisions, VB-03's identities, full evidence, and
both constructor and method observations.

### FINDING-02: the destination workspace is the documented write boundary

[validate_path](../../src/llm_wiki_cli/config.py#L125) intentionally constrains
wiki paths to cwd. The
[bootstrap option validator](../../src/llm_wiki_cli/services/bootstrap_runtime.py#L4330)
applies it independently from source-read permission. The
[README](../../README.md#L1364) explicitly says that `--wiki-dir` stays within
the runner project, including when the source lies elsewhere.

The probe verifies rejection before output creation from an unrelated cwd,
then success using the same source/output paths from the output workspace.
Doctor there returns healthy / exit 0 and source bytes are unchanged. Thus
dedicated storage is supported by anchoring the runner in that storage; this
is not a test-automation blocker requiring a validator change.

Use an absolute executable path after changing cwd: a relative
`.venv/bin/llm-wiki` would otherwise refer to a different environment. Any
future external-wiki feature needs separate, explicit output semantics.
Neither `--allow-external-src` nor `--source-adapter` authorizes arbitrary
external wiki writes by implication.

### FINDING-04: coherent snapshots can become stale while source is edited

The probe replaces only the fixture bootstrap's inventory-call wrapper. It
calls the real extractor, then appends a comment to the fixture source before
bootstrap resumes publication. This deterministically models the reported
in-flight change without background timing assumptions.

Bootstrap exits 0. Doctor then reports ready availability, valid snapshot
parity, two `nonsemantic-source-change` concepts and no `source-changed`,
`basis-incompatible`, or `source-missing` concepts. The non-strict result is
degraded / exit 1, exactly as specified by
[doctor classification](../../src/llm_wiki_cli/services/doctor_service.py#L585)
and the [documented exit-code contract](../../README.md#L1230).

An ordinary `sync --jobs 1` exits 0, restores the two concepts to current,
and doctor becomes healthy / exit 0. Generated content pages retain both
bytes and mtimes. This is effective drift detection and reconciliation, not
a broken manifest or a reason to lower health thresholds. A stable checkout
is the practical mitigation for repeatable generation; sync handles later
edits. A final mtime check could at most provide an advisory hint, since it
cannot eliminate edits after the check or reliably establish byte identity.
